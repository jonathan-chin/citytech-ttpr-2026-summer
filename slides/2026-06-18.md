# Follow Up: Mini Project Inspiration

The **Who's That Pokémon?** game you're building is inspired (in part) by **Framed**: https://framed.wtf/

- Framed shows a movie **one frame at a time**; each wrong guess reveals **another frame** (another hint)
- Same core loop as your project: **guess, get a hint, guess again**
- Progressive hints keep it fun: vague at first, easier with each reveal

---

# Follow Up: Plan Before You Code

**Starting a new project is hard.** Before writing code, take time to **brainstorm, diagram, and outline** your plan.

- Like an **essay outline**, a project outline makes the actual building far smoother
- Sketch your **routes, data, and game flow** before you implement them
- And just **play with the API** first: poke `pokeapi.co` in Insomnia or the browser to see what data comes back

A little planning up front saves a lot of debugging later.

# Follow Up: Navigating JSON

The JSON from PokéAPI can be **huge**. Explore it layer by layer instead of reading it all at once. `Object.keys(...)` gives the keys at the current level:

```js
console.log(Object.keys(pokemon));
// ["abilities", "moves", "height", "types", "cries", ...]
```

Then **zoom in** on a key. For arrays, index in and peek at that item's keys:

```js
console.log(Object.keys(pokemon.moves[0]));
// ["move", "version_group_details"]

console.log(Object.keys(pokemon.sprites));
// ["back_default", "front_default", ..., "other", "versions"]

console.log(Object.keys(pokemon.sprites.other));
// ["dream_world", "home", "official-artwork", "showdown"]
```

Repeat `Object.keys(...)` at each level until you reach the value you want.

# Technical Job Interviews

Many software jobs include a **technical interview**: you solve coding problems and/or answer technical questions live, in front of someone.

- Often **no IDE, no internet, and no AI assistant**: just you and the problem
- They test how you **think and communicate**, not only the final answer

---

# Whiteboard Coding

One common format is **whiteboard coding**: you write code by hand, on a whiteboard or in a plain editor, while explaining yourself.

- **Think out loud** so the interviewer can follow your reasoning
- **Clarify the problem** and ask about edge cases before you start
- **Plan first** (pseudocode or an outline), then write the code
- Don't stress over perfect syntax; aim for a clear, correct approach

---

# Coding Without AI

In most interviews, **AI tools are off-limits**: no Copilot, no ChatGPT, no autocomplete.

- Interviewers don't expect **perfect syntax**: just enough that they can tell what you're doing
- This is why we say: **never submit code you can't explain**
- **AI replaces labor; AI does not replace learning**
- So practice **coding by hand** sometimes, with no AI
